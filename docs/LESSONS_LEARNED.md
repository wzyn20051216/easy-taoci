# 从真实批量草稿写入中提炼的经验

本文只记录可公开复用的方法，不包含任何学生资料、导师名单、邮箱、浏览器会话或本地路径。

## 1. 先确认“能控制哪个浏览器”

用户说“我已经登录”不等于自动化工具能接管该浏览器。不同环境可能只有页面上下文、系统截图或命令行浏览器能力。正确顺序是：

1. 优先复用产品明确暴露的可控浏览器会话。
2. 无法控制普通浏览器时，启动带本地 CDP 端口的独立 Microsoft Edge。
3. 用户自行登录，自动化只在登录后的页面工作。

不能通过截图推断页面可操作，也不应索要密码或复制 Cookie。

## 2. 屏幕坐标适合诊断，不适合批量写入

多显示器、缩放比例、窗口焦点、浏览器缩放和页面重排都会让坐标点击漂移。短暂的坐标试验可以帮助确认窗口，但批量填写必须转为 DOM 自动化。否则容易产生空草稿、半成品或误点。

## 3. 同一页面可能同时存在多个写信模块

网易邮箱会保留隐藏的旧 compose 模块。简单使用 `.first` 或第一个同名按钮可能命中不可见元素。可靠策略是：

- 选择最后一个且 `is_visible()` 的输入框；
- 对“存草稿”按钮同时检查文字、边界框和可见性；
- 每封邮件打开新的 compose 路由，避免上一封残留；
- 失败时停在当前封，不继续污染后续草稿。

## 4. 正文编辑器位于 iframe

正文不是普通主页面输入框，需要定位 `body.isContentEditable` 的最新 iframe。直接设置 HTML 后应派发 `input` 和 `change` 事件，让邮箱页面感知内容变化。写入前要对纯文本进行 HTML 转义，避免内容被当作标签执行。

## 5. 附件出现文件名不等于上传完成

可靠的附件完成条件需要同时满足：

- 所有预期文件名出现在页面；
- “上传完成”数量达到附件数量；
- 页面不再含“待上传”或“请稍候”。

任何附件失败都应阻止保存成功状态，不能把“正文已填好”当成完整草稿。

## 6. 多邮箱字段需要明确主邮箱

邮箱页面对分号分隔的多个收件人解析可能不稳定。数据层保留全部官方邮箱，但草稿默认只使用第一个合法地址作为主邮箱。是否抄送或改用备用邮箱应由用户单独决定。

## 7. 成功必须有可恢复的证据

批量任务最怕“看起来跑完了”。每封草稿使用稳定哈希任务 ID，并在成功后立即追加状态记录。状态文件只记录 ID、结果和时间：

- 重跑时跳过已成功任务；
- 单封失败后从该任务继续；
- 不需要在日志中保存正文、姓名或邮箱；
- 可选截图用任务 ID 命名并留在私有工作区。

## 8. 草稿和发送是两个状态

“写进草稿箱”只授权创建草稿。追踪表必须保留：

- `草稿状态=已存草稿`
- `是否已发送=否`

公开工具不实现发送按钮，减少权限歧义和误操作风险。

## 9. 导师检索要先追求覆盖，再追求匹配

只搜索“学校 + 研究方向”会偏向搜索排名高的教师，漏掉学院名录中的其他候选。两遍检索更稳定：第一遍从官方名录枚举，第二遍逐页补方向、邮箱和近期招生证据。搜索摘要只定位页面，不支撑最终结论。

## 10. 内容质量来自证据链，不来自形容词

最有效的个性化不是长篇赞美，而是“具体研究方向 + 一项真实经历 + 希望继续学习的问题”。给学生经历稳定 ID，让每个匹配段回指 1-3 项事实，可以显著降低批量生成中的幻觉和事实漂移。

## 11. 节省 token 的关键是结构化复用

一次读取完整简历并提炼事实库，之后只传候选行和相关证据。排序、去重、占位符替换、附件检查、状态同步交给脚本。模型集中处理官网语义、匹配边界和自然表达，重复机械工作不再消耗上下文。

## 12. 发布前隐私检查要覆盖历史

`.gitignore` 只能防止新文件被跟踪，不能清除已经提交的内容。开源前应扫描当前树、检查暂存内容并查看 Git 历史。若敏感信息曾进入提交，应先重写历史并轮换相关凭据，再公开仓库。
